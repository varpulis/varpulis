What the engine does for a detection team

Sequences, not single events

A rule says what happened in order: this, then that, on the same host or across hosts, within a window. Negation, repetition, aggregates and joins are part of the language, so a kill chain is one rule rather than a chain of saved searches.

Log time, not arrival time

.within(2m) means two minutes between the timestamps in the logs, whatever order and delay they arrive with. A replay a week later raises the same alerts. A burst of late events cannot fake a match.

A crash does not lose a half-matched attack

Each rule saves its open sequences together with the position in the stream they stand for, and resumes from there after a restart. In the demo the process is killed with kill -9 between the two halves of an attack, and the alert still arrives.

Alerts are published before the input is acknowledged. After a crash an alert can be raised twice; it is never lost.

It reads what you already forward

Kafka, with offsets committed only after the alert is out. NATS JetStream. MQTT, AMQP and IBM MQ. An HTTP webhook for anything that can post. Your SIEM keeps its role; Varpulis needs a copy of the stream, not a migration.

Small enough to put next to anything

One 8 MB binary and about 10 MB of memory per rule set, no JVM. A correlation rule handles up to about 25 000 events per second on an ordinary eight-core machine, and the sizing is published: what costs is the number of attacks half-seen at once, not the number of events.

Open, down to the last rule

The engine, the runtime it ships on, the demo and the example rules mapped to MITRE ATT&CK are Apache-2.0 on GitHub. Read how it decides before you trust what it decides.

The rule that caught it

stream SmbServicePipe = Network
    .where(DestinationPort == 445)

stream RemoteServiceExec = Process
    .where(ParentImage.ends_with("\services.exe"))

stream LateralMovement = SmbServicePipe as smb
    -> RemoteServiceExec as exec
    .within(2m)
    .emit(
        rule: "lateral_movement_smb",
        mitre: "T1021.002",
        source_host: smb.Hostname,
        target_ip: smb.DestinationIp,
        remote_process: exec.Image
    )

Two filters and a sequence. The file name never appears, which is why renaming the binary changes nothing.

Written as a scheduled search, the same logic becomes a query joining two indexes over a time bucket, and a pair that straddles two buckets is missed. Here the window is part of the match.

The full rule, with its event declarations is 57 lines, most of them the Sysmon fields it reads.

See it in forty seconds

The demo runs two rules side by side on one bus: the signature above, and the behavioural sequence. It checks four things and says which held. This is a recording of one run, at real speed with a two-second pause between steps.

Press play to watch the run. To run it yourself:

# needs nats-server and the nats CLI on the machine
git clone https://github.com/cpoder/vejas && cd vejas
cargo build --release --manifest-path core/Cargo.toml
e2e/detect-demo/run.sh            # PAUSE=manual walks it step by step

Both rules fire on PsExec under its own name. The signature goes quiet when the binary is renamed, and the sequence still fires. Then the runtime is killed mid-sequence, restarted, and the alert arrives anyway. The same checks run on every commit.
